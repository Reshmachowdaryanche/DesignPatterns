# Factory Design Patterns — Java & Kotlin

## 1. Simple Factory Pattern

### Real-world example: Payment SDK

Imagine a payment SDK that supports Razorpay, Stripe, and PayPal.

The client specifies the payment provider. The factory creates the appropriate payment object, and the client calls `pay()` without directly creating the provider-specific object.

### Java implementation

```java
interface Payment {
    void pay(double amount);
}

class RazorpayPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paying using Razorpay: " + amount);
    }
}

class StripePayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paying using Stripe: " + amount);
    }
}

class PaymentFactory {
    static Payment create(String type) {
        if (type.equalsIgnoreCase("razorpay")) {
            return new RazorpayPayment();
        }

        if (type.equalsIgnoreCase("stripe")) {
            return new StripePayment();
        }

        throw new IllegalArgumentException(
            "Unknown payment provider: " + type
        );
    }
}

class Main {
    public static void main(String[] args) {
        Payment payment = PaymentFactory.create("razorpay");
        payment.pay(1000);
    }
}
```

### Kotlin implementation

```kotlin
interface Payment {
    fun pay(amount: Double)
}

class RazorpayPayment : Payment {
    override fun pay(amount: Double) {
        println("Paying using Razorpay: $amount")
    }
}

class StripePayment : Payment {
    override fun pay(amount: Double) {
        println("Paying using Stripe: $amount")
    }
}

object PaymentFactory {
    fun create(type: String): Payment =
        when (type.lowercase()) {
            "razorpay" -> RazorpayPayment()
            "stripe" -> StripePayment()
            else -> throw IllegalArgumentException(
                "Unknown payment provider: $type"
            )
        }
}

fun main() {
    val payment = PaymentFactory.create("razorpay")
    payment.pay(1000.0)
}
```

### How it works

1. Client passes the provider type to the factory.
2. Factory selects the concrete payment implementation.
3. Factory returns the object through the `Payment` interface.
4. Client calls `pay()`.

### Advantages

- Simple to understand and implement.
- Centralizes object-creation logic.
- Reduces direct dependencies on concrete payment classes.
- Useful when the number of supported types is small and stable.

### Disadvantages

- Adding a provider requires modifying the factory's conditional logic.
- The factory can grow as the number of implementations increases.
- Creation logic can become difficult to maintain if many unrelated types are handled.

### Interview answer

"Simple Factory centralizes object creation in one class. In a payment SDK, the client passes a provider type such as Razorpay or Stripe, and the factory returns the corresponding Payment implementation. The client uses the Payment interface without creating provider-specific objects directly."

**Note:** Simple Factory is a common idiom, not one of the original 23 GoF design patterns.

## 2. Factory Method Pattern

### Real-world example: Payment SDK

We have the same payment SDK, but now each provider has its own factory.

Instead of a single factory using conditional logic, a concrete factory decides which payment object to create.

### Java implementation

```java
interface Payment {
    void pay(double amount);
}

class RazorpayPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paying using Razorpay: " + amount);
    }
}

class StripePayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paying using Stripe: " + amount);
    }
}

abstract class PaymentFactory {
    abstract Payment createPayment();

    public void processPayment(double amount) {
        Payment payment = createPayment();
        payment.pay(amount);
    }
}

class RazorpayFactory extends PaymentFactory {
    @Override
    Payment createPayment() {
        return new RazorpayPayment();
    }
}

class StripeFactory extends PaymentFactory {
    @Override
    Payment createPayment() {
        return new StripePayment();
    }
}

class Main {
    public static void main(String[] args) {
        PaymentFactory factory = new RazorpayFactory();
        factory.processPayment(1000);
    }
}
```

### Kotlin implementation

```kotlin
interface Payment {
    fun pay(amount: Double)
}

class RazorpayPayment : Payment {
    override fun pay(amount: Double) {
        println("Paying using Razorpay: $amount")
    }
}

class StripePayment : Payment {
    override fun pay(amount: Double) {
        println("Paying using Stripe: $amount")
    }
}

abstract class PaymentFactory {
    protected abstract fun createPayment(): Payment

    fun processPayment(amount: Double) {
        val payment = createPayment()
        payment.pay(amount)
    }
}

class RazorpayFactory : PaymentFactory() {
    override fun createPayment(): Payment =
        RazorpayPayment()
}

class StripeFactory : PaymentFactory() {
    override fun createPayment(): Payment =
        StripePayment()
}

fun main() {
    val factory: PaymentFactory = RazorpayFactory()
    factory.processPayment(1000.0)
}
```

### How it works

1. Client selects a concrete factory, such as `RazorpayFactory`.
2. Client calls `processPayment()`.
3. The shared workflow invokes `createPayment()`.
4. Polymorphism invokes the concrete factory's overridden method.
5. The factory creates and returns the corresponding Payment object.
6. The workflow calls `pay()` on that object.

### Advantages

- Separates object creation from the shared workflow.
- Supports extending the design with new concrete factories and products.
- Avoids a growing conditional-based creation method.
- Encourages programming to interfaces.

### Disadvantages

- Requires more classes than Simple Factory.
- The client or configuration must select a concrete factory.
- May introduce unnecessary complexity for a small, stable set of implementations.

### Interview answer

"Factory Method defines a method for creating a product and lets subclasses decide which concrete object to instantiate. In a payment SDK, RazorpayFactory creates RazorpayPayment and StripeFactory creates StripePayment. The shared payment workflow uses the Payment interface, so adding a new provider can often be done by adding a new factory and product rather than modifying existing creation logic."

Factory Method is one of the original 23 Gang of Four design patterns.

## 3. Simple Factory vs Factory Method

| Feature | Simple Factory | Factory Method |
|---|---|---|
| Object creation | One factory chooses the implementation | Concrete factory subclasses choose |
| Typical mechanism | `if` / `switch` | Overriding and polymorphism |
| Number of classes | Fewer | More |
| Adding a provider | Usually modify factory logic | Add a concrete factory and product |
| Complexity | Lower | Higher |
| Best suited for | Small, stable sets of types | Systems requiring extensible creation behavior |

### Important distinction

Simple Factory:
```java
Payment payment = PaymentFactory.create("razorpay");
```

Factory Method:
```java
PaymentFactory factory = new RazorpayFactory();
factory.processPayment(1000);
```

The first selects a product using a type passed to one factory. The second delegates product creation to a concrete factory subclass.

## 4. Common Interview Questions

### Q1. Why use a factory?

To separate object creation from object usage and reduce direct coupling to concrete classes.

### Q2. Why return a Payment interface?

So client code can use different payment implementations through the same contract.

### Q3. Which pattern is better?

Neither is universally better. Simple Factory is easier for a small set of types. Factory Method is useful when creation behavior varies by subclass and extensibility justifies the extra classes.

### Q4. Does a factory eliminate the `new` keyword?

No. The factory often uses `new` internally. It hides creation details from the client.

### Q5. Is a factory always a singleton?

No. A factory can be a regular object, an instance, a static utility, or a singleton. Kotlin's `object` is one way to implement a singleton factory.

### Q6. How do these patterns relate to the Open/Closed Principle?

Factory Method can support extension without changing existing creation classes. Simple Factory's conditional logic typically needs modification when adding a new type. Neither pattern automatically guarantees the Open/Closed Principle for the entire application.

## 5. Quick Revision

- **Simple Factory:** One factory selects which object to create.
- **Factory Method:** Concrete factory subclasses decide which object to create.
- **Common benefit:** Separate creation logic from client usage.
- **Simple Factory trade-off:** Easier to implement, but conditional logic grows.
- **Factory Method trade-off:** More extensible creation structure, but more classes.
- **Key principle:** Program to an interface, not an implementation.

### One-line memory trick

Simple Factory = **one factory with selection logic**.

Factory Method = **subclasses decide object creation through overriding**.
